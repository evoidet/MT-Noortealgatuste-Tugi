## Причины и исправления загрузки фотографий

Обе проблемные фотографии — JPEG 1200×750. Лагерь занимает 200 497 байт, Erasmus+ — 71 480 байт. Это не многомегабайтные оригиналы: существенная часть проблемы связана с доставкой и выбором файлов.

Фотографии находятся в существующем приватном Vercel Blob и публикуются через разрешённый публичный API. При промахе CDN запрос проходит серверную функцию, проверки публикации/вложения в БД и чтение Blob. В каталоге использован домен без `www`, перенаправляемый на `www`. На рабочем сайте нет нового модуля оптимизации. Дополнительно найдено и исправлено условие в подготовленной версии: оно считало два официальных домена разными источниками и пропускало оптимизированные варианты.

Сборка теперь скачивает только уже опубликованные изображения из собственного каталога через разрешённый публичный маршрут и создаёт статические варианты WebP/AVIF. Произвольные хосты, приватные пути, URL с учётными данными и параметрами исключены. Загрузка ограничена по времени и объёму; если публичный файл недоступен, сохраняется существующий API-вариант. Новое хранилище не добавлено.

Манифест имеет приоритет перед динамическим API. Для известных изображений браузер запрашивает файл `/assets/responsive/<content-hash>-<width>.<format>` напрямую; в проверенных посещениях исходный API не вызывался. Для этих файлов уже настроен годовой `immutable`-кэш, а изменение содержимого меняет имя. Оригиналы сохранены для открытия фотографии полностью. Для ещё не попавших в сборку изображений остаются ограниченные серверные преобразования.

`srcset` и `sizes` выбирают размеры отдельно для карточки, главной новости и полной статьи. Обложка статьи загружается приоритетно, изображения ниже экрана — лениво; пропорции обложки зарезервированы. Сборка обработала **66 изображений** по всему сайту. Статические HTML-фотографии поддерживают AVIF с WebP-резервом; динамические новости в этой реализации выбирают WebP.

## Измерения

Проверены настоящие фотографии двух статей в локальной сборке Chromium. Для каждого посещения создавался новый контекст с пустым кэшем. В варианте «до» отключался выбор responsive-файлов; разметка статьи оставалась той же. Значения — переданный размер самой обложки, не размер всей страницы.

| Изображение / экран | До, байт | После, байт | Сокращение |
| --- | ---: | ---: | ---: |
| Лагерь, 390 px, DPR 1 | 200 497 | 39 110 | 80,5% |
| Erasmus+, 390 px, DPR 1 | 71 480 | 15 064 | 78,9% |
| Лагерь, 390 px, DPR 2 | 200 497 | 130 470 | 34,9% |
| Erasmus+, 390 px, DPR 2 | 71 480 | 32 264 | 54,9% |
| Лагерь, 1440 px, DPR 1 | 200 497 | 198 072 | 1,2% |
| Erasmus+, 1440 px, DPR 1 | 71 480 | 42 020 | 41,2% |

Для фотографии лагеря на большом экране экономия WebP небольшая; здесь основной выигрыш — исключение API/БД/Blob из обычной доставки. Размер не уменьшался ценой чрезмерного сжатия. Скриншоты обеих обложек проверены визуально: явных артефактов или нарушения пропорций не обнаружено. Это визуальная проверка, а не утверждение о побитовом совпадении.

Отдельные HTTP-замеры действующего сайта до публикации: лагерь 418 мс при первом запросе и 162 мс при повторном; Erasmus+ 155 и 148 мс. Во всех случаях CDN сообщил `HIT`. Эти числа не измеряют холодный запуск сервера и не доказывают отсутствие периодических задержек. Измерения скорости и Core Web Vitals после production-публикации пока отсутствуют; локальные миллисекунды не выдаются за ускорение рабочего сайта.

## Что ещё требуется для завершения на production

1. Доступ к Vercel и определение проекта, обслуживающего `noortetugi.ee`/`www.noortetugi.ee`. GitHub показывает несколько Vercel-проектов; успешный preview одного из них не подтверждает обновление рабочего домена.
2. Подтверждение резервной копии БД перед production-сборкой: текущий штатный build автоматически запускает миграции. Это соответствует исходному требованию владельца не менять production-данные без проверки и резервной копии.
3. Выпуск ветки, штатная проверка БД и `check-staff-identities.mjs`, затем вход обоих реальных пользователей и проверка финансовых прав. Настройки окружения предполагаются корректными и не читаются из секретных файлов; доступность настроенного статуса НДС нужно подтвердить через приложение. При отсутствии статуса приложение блокирует выпуск новых документов.
4. Проверка PDF и доставки в рабочей среде только с явно выбранным владельцем адресатом, затем повторные измерения изображений и страницы с пустым кэшем.
